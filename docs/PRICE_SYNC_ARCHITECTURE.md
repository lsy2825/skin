# 가격 데이터 동기화 구조 (Price Sync Architecture)

기준일: 2026-10-14. 코드: `build2/datameta.py`, `app/domain/sync.js`, `app/app.js`의 `loadData`·`paintSync`, `app/gate.js`(첫 방문 미리 받기), `app/sw.js`. 테스트: `tests/sync.test.js`(5개), `tests/e2e/data_sync.js`(13개), `tests/e2e/pricenow.js` S19·S20.

## 1. 먼저 잰 것 (측정 후 필요한 부분만)
| 항목 | 값 | 근거 |
|---|---|---|
| `app/data.json` | 5,713,226 바이트, 압축(gzip) 795,446 바이트 | 2026-10-14 파일 |
| 가장 큰 부분 | 가격 열(cols) 압축 358KB, 글자 표(s) 241KB, 메타(분류·지식) 52KB, 이력(trend) 42KB | 섹션별 측정 |
| 하루 사이 두 빌드의 차이 | 가격 줄 13개 빠짐(이벤트 종료), 나머지 같음 | `datameta.py` 비교 |
| 같은 두 빌드의 글자 표 | 29,438개 중 16,114개만 같은 번호 | 위와 같은 비교 |
| 느린 4G 첫 방문 | 가격이 보이기까지 8.8초(미리 받기 있을 때), 12.0초(없을 때) | `QA_REPORT.md` 성능 |

결론:
- **재방문**이 가장 큰 낭비였어요. 바뀌지 않았어도 매번 조건부 요청을 보내고, 5.7MB를 다시 읽어 색인을 만들었어요. → **버전 확인**으로 해결.
- **첫 방문**은 파일 하나를 끝까지 받아야 해요. 지점 단위로 나누는 건 구조 변경이 커요(§5). → **실제 진행률**과 **미리 받기 유지**로 해결.
- 바뀐 줄만 받는 패치는 글자 표 번호가 빌드마다 바뀌어서 지금은 할 수 없어요(§5).

## 2. 흐름
```
빌드(GitHub Actions, build2/appdata.py)
  ├─ app/data.json            (가격 전체)
  ├─ app/home.json            (홈 화면이 쓰는 비교 키의 모든 줄만, build2/homedata.py — O2, 약 1/10)
  └─ app/data-meta.json       (≈1KB: schema, version, updated, built, bytes, sha256, rows, branches,
                               verified, stale, brands[], home{bytes, sha256, rows}, changes{from, price[], added[], removed[], counts})

앱(app.js loadData) — 한 번에 하나만 실행(두 번째 '다시 시도'는 같은 작업에 합류)
  1. 휴대폰 사본 읽기(Cache Storage 'pc-data-v1': current-meta → data-<version>)  ┐ 동시에
  2. data-meta.json 받기(cache: no-store)                                         ┘
  3. 사본이 검사를 통과하면 바로 화면에 표시
  4-a. 서버 버전 = 사본 버전 → 끝(가격 파일 요청 0번)
  4-b. 서버에 닿지 못함 → 사본 + "저장된 가격 정보입니다. 현재 가격과 다를 수 있습니다."
  4-c. 새 버전 → 사본을 보여둔 채 뒤에서 받기(PARTIALLY_READY) → 검사 → 저장 → '새 가격 보기'
  4-d. 사본 없음(첫 방문) → home.json 받기 → 메타의 home.sha256과 같으면 홈 화면 표시(저장 안 함)
       → data.json을 진행률과 함께 받기 → 검사 → 저장 → 전체로 바꿔 다시 그림
       (home.json이 없거나 체크섬이 다르면 예전처럼 data.json만 기다림)
```
- 첫 방문에는 `gate.js`가 앱 스크립트보다 먼저 `home.json` 요청을 시작해요(사본이 없을 때만). data.json은 `gate.js`가 home.json을 다 받자마자 시작해요(동시에 받으면 둘이 대역폭을 나눠 홈이 늦어지고, 앱 스크립트를 기다렸다 시작하면 전체 가격이 4초쯤 늦어졌어요 — 첫 측정). 예전 HTML 미리 받기(`<link rel=preload>`)는 재방문에도 요청을 보내서 뺐어요.
- **home.json으로 그린 홈의 숫자는 전체 파일과 같아요.** 홈이 보여줄 수 있는 비교 키(인기 6개, 분류 탭마다 큰 시술 6개의 대표 옵션, 오늘의 발견 후보 80개, 가격 변동 키)의 줄을 **지점 전부** 담아서, 지역·브랜드·부가세·위치 설정이 무엇이든 앱이 같은 코드로 같은 값을 계산해요. 줄에서 셀 수 없는 것(전체 시술 개수, 분류 목록, 시술군별 판매 지점 수)은 `meta.partial`에 전체 파일 기준으로 넣었어요. 확인: `tests/homedata.test.js`(파일 대조), `tests/e2e/o2_home.js`(홈 탭 9개·발견 목록을 home.json 상태와 전체 상태에서 비교, 기본·전국+부가세 포함 설정).
- 전체 파일이 오기 전에는 홈만 열려요. 다른 화면은 "전체 가격을 받는 중… N%"를 보여주다가 도착하면 바로 열리고, 홈에서 친 검색과 '담기'는 도착 뒤에 이어서 해요. 장바구니 합계 띠·알림 검사·계정 동기화·저장 항목 이동(keymap)도 전체 파일 뒤에만 해요.
- 새 버전이 준비되면 화면의 데이터를 몰래 바꾸지 않아요. 열린 창·보던 목록이 엉키지 않게, 안내 줄의 **'새 가격 보기'**를 누르면 새 사본으로 다시 열어요. 누르지 않아도 다음에 열 때 새 사본이 쓰여요.

## 3. 상태 (`Sync.stateOf`)
| 상태 | 언제 | 화면 |
|---|---|---|
| (O2) 홈 요약 | 첫 방문, home.json으로 홈을 그리고 data.json을 받는 중(`SYNC.partial`) | 머리말 날짜 자리에 "전체 가격을 받는 중… N%"(글자만 바뀜 — 안내 줄을 띄우면 화면이 밀렸다 돌아와 CLS 0.086이 생겨서 뺐어요). 실패하면 안내 줄 "전체 가격을 받지 못했어요. 홈 가격만 보여요 · 다시 시도" |
| LOADING | 사본 없이 받는 중 | 죠미(졸린 표정) + "오늘의 가격을 살펴보는 중… 45% (2.6/5.7MB)", 다 받으면 "받은 가격을 정리하는 중…" |
| PARTIALLY_READY | 사본을 보여주며 새 버전을 받는 중 | 머리말 점(깜빡임) + 안내 줄 "저장된 가격 표시 중 · 새 가격 받는 중 N%" |
| READY | 서버 버전과 같은 데이터, 8일 이내, 실패 지점 없음 | 머리말 점(초록) |
| STALE | 서버에 닿지 못해 사본만(오프라인) 또는 데이터가 8일보다 오래됨 | 안내 줄 "저장된 가격 정보입니다. 현재 가격과 다를 수 있습니다." / "가격이 N일 전 것이에요" |
| PARTIALLY_FAILED | 이번 수집에서 일부 지점이 실패해 지난 자료를 씀 | 데이터 상태 화면 'N곳은 지난 가격', 가격 옆 '지난 자료' |
| ERROR | 사본도 없고 받기도 실패 | 오류 화면 + 이유(예: "체크섬이 달라요 … (3번 시도)") + 다시 시도 |

'실시간'이라는 말은 쓰지 않아요(라벨 테스트로 확인).

## 4. 무결성 (저장 전에 확인)
| 확인 | 어디서 |
|---|---|
| 메타 형식: schema = 1, version = `YYYY-MM-DD.<sha 앞 8자>`, sha256 64자, 크기·줄 수·지점 수 | `Sync.checkMeta` |
| 데이터 형식: meta·branches·cols·keys·s가 있음, 모든 열이 줄 수와 같음, 같은 지점 두 번 없음 | `Sync.checkData` |
| 메타와 일치: SHA-256(받은 바이트) = meta.sha256, 날짜·줄 수·지점 수 일치 | 〃 (`crypto.subtle`) |
| home.json: SHA-256 = meta.home.sha256(같은 빌드), 형식·날짜·줄 수·지점 수, `meta.partial` 모양. 휴대폰에 저장하지 않음 | `Sync.checkHome` |
| 원자적 교체: 새 파일을 `data-<version>`으로 먼저 저장 → 그다음 `current-meta` 포인터 → 옛 버전 삭제 | `cachePut` |
| 실패 시: 다시 받기 1초·3초 뒤(모두 3번). 끝내 실패하면 **마지막 정상 사본** 유지 + "새 가격을 받지 못해 저장된 가격을 보여줘요 · 다시 시도" | `loadData` |
| 읽은 사본이 깨졌으면: 화면에 쓰지 않고 지우고 새로 받음 | 〃 |
| 서비스 워커는 가격 파일(data·data-meta·home.json)을 건드리지 않음(앱이 검사한 사본만 씀). 새 서비스 워커가 옛 캐시를 지울 때 `pc-data-*`는 남김 | `sw.js` |
| 취소: 받는 중 '저장된 가격 지우고 다시 받기'를 누르면 진행 중인 요청을 멈춤(AbortController) | `deviceCard` |

## 5. 하지 않은 것과 조건
| 항목 | 왜 안 했나 | 하려면 |
|---|---|---|
| 줄 단위 증분 패치(바뀐 줄 ID·삭제 표시로 사본을 고치기) | 글자 표·묶음·통계가 빌드마다 번호를 새로 매겨요(같은 날 두 빌드도 글자 번호 45%가 달라짐). 지금 패치를 만들면 패치가 파일만큼 커지거나 틀린 번호를 가리켜요 | ① 글자 표 번호 고정(이전 표를 이어 쓰고 새 글자만 뒤에) ② 묶음·통계를 줄 번호가 아닌 키로 ③ 패치에 이전·다음 SHA를 넣어 맞을 때만 적용 |
| 지점 단위로 나눠 받기·받은 지점부터 검색 | 지점 수·중간값·비교 키 묶음이 전국 데이터를 기준으로 계산돼요. 일부만 받은 상태의 통계는 틀려요 | 지점별 파일 + 앱에서 통계 재계산 + '부분 결과' 표시. 데이터가 지금의 몇 배가 되면 검토 |
| IndexedDB 색인 저장 | 사본에서 색인을 다시 만드는 시간보다 저장·검증 비용이 비슷하거나 커요(재방문은 이미 다운로드 0) | 측정 후 필요하면 |

**바뀐 줄 목록(`changes`)은 만들었어요.** 지난 수집본과 비교해 가격이 바뀐 줄, 새로 생긴 줄, 빠진 줄을 이름으로 적어요(목록은 각 300개까지, 개수는 전부). 데이터 상태 화면의 '이번 갱신에서 바뀐 가격'이 이걸 보여줘요. 2026-10-14 실제 값: 가격 바뀜 0, 새로 생김 0, 빠짐 13.

## 6. 휴대폰에 저장하는 것
| 저장소 | 내용 | 개인정보 |
|---|---|---|
| Cache Storage `pc-data-v1` | 검사를 통과한 data.json 한 벌 + 그 메타 | 없음(공개 가격 파일) |
| localStorage `pc:*` | 기존 설정·장바구니·관심·알림 + `rechecks`(재확인 요청 날짜, 30일) | 건강 관련 자유 입력은 저장하지 않아요(피부 고민 입력은 원래부터 저장 안 함) |

PIN은 화면 잠금일 뿐 데이터 접근 통제가 아니에요. data.json은 공개 파일이에요.
