# 가격 재확인 설계 (Price Refresh)

기준일: 2026-10-14. 코드: `app/app.js`의 `recheckSheet`(이 가격 다시 확인하기), `top3Card`(장바구니 맨 위 3곳), `recheckQueue`(재수집 순서). 테스트: `tests/e2e/pricenow.js` S14·S15.

## 1. 지금 되는 것과 안 되는 것
| | 지금(시연 단계) | 재수집 서버가 생기면 |
|---|---|---|
| 버튼 이름 | '이 가격 다시 확인하기', '3곳 재확인 요청' | '지금 다시 확인' |
| 누르면 | ① 윤실장이 가진 기록(병원 가격을 읽은 날, 이번 주 수집 성공·실패, 원본 대조 결과, 앱 데이터 버전, 이 휴대폰이 서버 버전을 확인한 시각, 다음 정기 수집일) ② 병원 원본 페이지 열기 ③ 운영자에게 **실제** 재확인 요청(GitHub 공개 이슈, 라벨 `price-recheck`) | 요청 접수 → 작업 상태(대기·진행·완료·실패) → 결과(같음·바뀜·찾지 못함) → 갱신 시각 → 원본 링크 |
| 병원 사이트를 바로 다시 읽나 | **아니요.** 화면에 그렇게 적어요("버튼을 눌러도 병원 사이트를 바로 다시 읽지 않아요") | 예(요청 제한 안에서) |
| '새로고침'과의 구분 | 앱 데이터 다시 받기는 '데이터 상태 → 저장된 가격 지우고 다시 받기'(이미 모아 둔 파일을 다시 받는 것)로 따로 둬요. 재확인 요청과 섞지 않아요 | 같음 |

## 2. 요청 제한 (지금)
- 같은 가격(지점 + 상품명 + 병원 표시가)은 **하루 한 번**. 두 번째로 열면 "오늘 이미 요청했어요"만 보여요.
- 이 휴대폰에서 **하루 10번**까지.
- 기록은 `pc:rechecks`(이 휴대폰, 최근 30일, 100개까지)에 남아요.
- 공개 글이라 개인정보를 적지 말라고 안내해요.

## 3. 재수집 서버가 생기면 (설계)
| 요소 | 설계 |
|---|---|
| 요청 | `POST /recheck {branch, row}` — 로그인 없이도 가능하지만 IP·기기별 제한 |
| 중복 제거 | 같은 지점에 이미 대기·진행 중인 작업이 있으면 새 작업을 만들지 않고 그 작업을 돌려줌 |
| 지점별 간격 | 같은 지점은 최소 30분 간격(병원 사이트 부담). 실제 값은 사이트별 robots·약관 검토 후 `scrape/sources.py` REGISTRY의 rate에 맞춤 |
| 비용 보호 | 전체 동시 작업 수 상한, 시간당 요청 상한, 실패가 이어지는 지점은 자동 보류 |
| 재시도 | 일시 오류는 1·5·15분 뒤 최대 3번, 차단(403·429·CAPTCHA)은 **재시도·우회하지 않고** 운영자 확인으로 넘김 |
| 결과 | 원본에서 같은 이름·가격을 찾으면 FOUND, 이름만 있으면 NAME_ONLY … (지금의 `scrape/verify_prices.py` 판정과 같은 규칙) |
| 앱 반영 | 결과를 `data-meta.json`처럼 버전이 있는 작은 파일 또는 API로. 앱은 결과가 나오기 전까지 '확인 중', 나온 뒤 '확인 HH:MM' |

**하지 않을 것:** 접근 제한 우회, CAPTCHA 풀기, 차단 회피용 IP 바꾸기, 로그인이 필요한 페이지 읽기.

## 4. 수집 일정 감사 (현재)
- `weekly.yml`: 매일 06:00(KST) 판단 → 월요일 정기 수집 + 저장된 이벤트가 끝난 다음 날 수집(`build2/needs_refresh.py`). 앱·빌드 코드가 바뀌면 수집 없이 다시 빌드.
- 지점마다 한 번 읽고, 실패하면 지난 자료를 STALE로 유지(30% 넘게 줄면 지난 자료 사용).
- 초저가 원본 대조: `price-check` 워크플로(수동).
- 참고 사이트의 "6시간·24시간마다"는 **약속하지 않아요.** 서버 용량과 병원 사이트 허용 범위가 정해지지 않았어요.

## 5. 재수집 우선순위 (계산은 구현, 스케줄러 연결은 BACKEND_REQUIRED)
`recheckQueue()`가 지점마다 점수를 매겨요. 운영 현황 화면에 상위 10곳과 이유가, 데이터 상태 화면에 곳 수가 보여요.

| 이유 | 점수 |
|---|---|
| 확인한 지 8일 이상 | 지난 일수 |
| 이번 주 수집 실패(STALE) | +10 |
| 7일 안에 끝나는 이벤트 | 개수(최대 +10) |
| 급변 검토 대기 | 개수 × 3 |
| 원본 대조 불일치(이름만·없음·읽기 실패) | 개수 × 2 |
| 지난주 가격 변동이 있었음 | +1 |

지금 수집기는 매주 모든 지점을 읽어서 이 순서를 쓰지 않아요. 재수집 서버가 생기면 이 순서대로 오래된 지점부터 읽게 돼요.
