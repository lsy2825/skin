# 보안 감사 (Phase 1 — Security Audit)

기준일: 2026-10-13. 대상: 저장소 `lsy2825/skin`의 전체 코드와 git 기록 39개 커밋. 운영 중인 서비스는 https://lsy2825.github.io/skin/ 이에요.
- 고친 내용: `SECURITY_REMEDIATION.md`
- 테스트 결과: `SECURITY_TEST_REPORT.md`
- 구조와 통제: `SECURITY_ARCHITECTURE.md`

## 방법
- 코드를 전부 읽었어요. 별도 에이전트가 읽기 전용으로 점검했고, 보고된 항목은 해당 줄을 다시 열어 직접 확인했어요.
- 현재 파일과 git 기록 전체에서 비밀 정보 패턴을 찾았어요(`tests/security/scan_secrets.py`).
- 데이터베이스 정책은 로컬 PostgreSQL 16에서 공격 시나리오로 시험했어요(Supabase 대역 사용).
- 브라우저에서 악성 입력 시험을 했어요(Playwright·Chromium).
- **하지 않은 것**
  - 실제 Supabase 프로젝트 시험: 아직 없어요. 로그인 키는 사용자 결정으로 보류 중이에요.
  - 운영 사이트에 대한 공격 시험
  - 외부 침투 시험

## 지금 시스템의 실제 모습 (공격 표면)
| 구성 | 상태 | 공개 범위 |
|---|---|---|
| 앱(`app/`) | 운영 중. GitHub Pages 정적 파일 | 누구나 받을 수 있어요(비밀번호 화면은 화면만 가림) |
| 가격 데이터(`app/data.json`) | 운영 중 | 공개 파일이에요 |
| 저장소 | 운영 중 | **공개 저장소**예요(코드·데이터·기록 모두) |
| 수집·배포(GitHub Actions) | 운영 중 | 저장소 쓰기 권한자만 실행·수정할 수 있어요 |
| 사용자 데이터 | 운영 중 | 각자 휴대폰 localStorage에만 있어요. 서버로 보내지 않아요 |
| 로그인·DB(Supabase) | **설계만 있고 미배포**(키가 비어 있음) | 해당 없음 |

그래서 아래 결과는 두 가지로 나눠요.
- **확인된 취약점:** 지금 운영 환경에서 실제로 영향이 있어요.
- **잠재 위험:** DB를 배포하거나 조건이 맞을 때 영향이 생겨요.

**1번: PIN이 적혀 있던 곳**
- `NOTES.md:5`
- 화면 테스트 4개 파일: `tests/e2e/*.js`. 제가 이전 작업에서 쓴 거예요.

**4번: localStorage 세부**
- 저장되는 정보
  - 프로필: 닉네임·성별·나이대
  - 시술 기록(가격·메모), 장바구니, 알림, 검색 기록
  - 집·직장 좌표
- 이 정보는 같은 출처(`lsy2825.github.io`)의 **다른 GitHub Pages 사이트**도 읽을 수 있어요.
- 로그인을 켜면 세션 토큰도 여기에 저장돼요(잠재 위험).
- 완화한 것: 좌표를 약 1 m 단위에서 약 100 m 단위로 낮췄어요. CSP를 추가했어요.
- 남은 것: 전용 도메인이 있어야 출처 공유 문제가 해결돼요.

**6번: 접근 통제 세부**
- `schema_platform.sql`의 표 16개(파티션 포함)에 RLS가 하나도 없었어요.
  - Supabase에 그대로 올리면 공개 anon 키만으로 누구나 가격·감사 기록·신고를 쓰고 지울 수 있었어요.
  - 뷰 `current_offers`는 정책을 우회했어요.
- 가격 알림이 **남의 장바구니**를 가리킬 수 있었어요(`price_alerts`).

**7번: XSS 세부**
- 화면 출력은 텍스트 노드와 `setAttribute`만 써요.
- **잠재 위험 1:** 수집한 원본 URL이 `javascript:`이면 그대로 링크가 됐어요. 지금 데이터는 모두 https예요.
- **확인된 결함 1:** CSP가 없었어요.
- **확인된 결함 2:** 공유 장바구니 링크(`#import/…`)를 반쯤만 검사했어요. 이상한 값을 넣으면 화면이 비고, 모르는 필드가 저장됐어요.

**8번: 인젝션 세부**
- **확인된 취약점:** 워크플로 `price-check.yml`의 입력값이 셸 명령에 그대로 들어갔어요. 악용하려면 저장소 쓰기 권한이 필요해요.
- 정상인 부분
  - SQL은 CSV `\copy`로 넣어서, 수집 문자열이 SQL로 해석되지 않아요.
  - 동적 SQL은 `format('%I')`로만 만들어요.

**9번: 무단 데이터 수정 세부**
- **확인:** 가격 데이터는 저장소에 커밋으로 들어가요. 저장소 쓰기 권한이 있으면 누구나 바꿀 수 있어요(main 브랜치 보호 없음).
- **확인:** 워크플로 권한이 작업 전체에 넓게 주어져 있었어요.
- **잠재 위험:** DB 쪽 쓰기에는 제한이 없었어요(6번).

**10번: 의존성 세부**
- 확인된 것
  - 파이썬 패키지 버전이 고정되지 않았어요(`>=`).
  - GitHub 액션을 태그로만 고정했어요.
- 잠재 위험: 로그인 라이브러리를 CDN에서 무결성 검사 없이 불러왔어요.
- Leaflet 1.9.4는 알려진 CVE를 모르겠어요. 실시간 취약점 DB로는 확인하지 않았어요.

## 정상으로 확인한 것
- `eval`, `new Function`, `document.write`, 문자열 `setTimeout`, `insertAdjacentHTML`을 쓰지 않아요.
- `innerHTML`은 고정된 SVG 2개에만 써요.
- `target=_blank` 링크 13개 모두 `rel=noopener`가 있어요.
- 사용자 데이터 스키마(`schema.sql`)
  - 6개 표 모두 RLS와 `auth.uid()` 정책이 있었어요.
  - `delete_me`는 경로가 고정돼 있고 anon 실행이 막혀 있어요.
- 수집기
  - `verify=False`가 없어요.
  - 시간 제한이 있어요(25초).
  - 읽는 주소는 고정 호스트나 정규식으로 제한돼 있어요(SSRF 없음).
- 서비스 워커는 다른 출처의 응답을 캐시하지 않아요.
- 워크플로에 `pull_request_target`이 없어요.

## 기기에 저장하는 정보 (개인정보 점검, 2026-10-13 v5.0)
코드에서 `store.set`·`localStorage`·`sessionStorage`를 모두 찾아 정리했어요. 모두 사용자의 휴대폰 안에만 있고 서버로 보내지 않아요(로그인을 켜면 장바구니·프로필·기록만 계정에 동기화).
| 묶음 | 키(`pc:` 접두사) | 민감도 | 지우는 방법 |
|---|---|---|---|
| 장바구니·관심 | `carts`, `ci`, `favs`, `presets`, `alerts`, `notes` | 낮음 | 각 화면에서 지우기(되돌리기 있음) |
| 설정 | `special`, `vat`, `brands`, `nbrands`, `noStack`, `sort`, `cmpView`, `tableSort`, `theme`, `region`, `when`, `histOff` | 낮음 | 마이 → 설정 초기화(일부) |
| 위치 | `places`(집·직장, 약 100m 단위로 줄임), `locPlace` | 중간 | 거리 기준 위치 시트(헤더 위치 버튼) → '저장한 집·직장 지우기'(2026-10-13 추가, 되돌리기 있음) |
| 보기 기록 | `recent`, `recentQ`, `lastRoute` | 중간(관심 시술이 드러남) | **마이 → 보기 기록: '기록 지우기', '기록 남기기' 끄기(2026-10-13 추가)** |
| 프로필·시술 기록 | `me`(닉네임·성별·나이대), `recs`(받은 시술) | **높음(건강 관련)** | 마이 → 받은 시술 기록마다 지우기, 프로필 시트에서 고치기 |
| 기타 | `reports`(보낸 신고 목록), `sender`, `jomiSeen` | 낮음 | — |
| 비밀번호 화면 | `pc:gate`(틀린 횟수·잠금 시각), sessionStorage `pc:gate-ok` | 낮음 | 탭을 닫으면 잠금 해제가 사라져요 |
- **피부 고민 문장은 저장하지 않아요.** 기기 안에서 규칙으로 분류하고 버려요(`AI_CONCERN_DISCOVERY_SPEC.md`).
- 쓰이지 않던 `lastTable` 키는 더 이상 쓰지 않고, '기록 지우기'가 예전 값도 지워요.
- 남은 일: 공개 전 개인정보 처리방침에 위 목록을 그대로 적어야 해요(`RELEASE_CHECKLIST.md` 1장).

## 결론
지금 플랫폼이 "안전하다"고 말할 수는 없어요.
- 확인된 취약점 가운데 **PIN 노출은 PIN을 바꾸기 전까지 해결되지 않아요.**
- GitHub 보안 설정은 이 작업 환경에서 바꿀 수 없어서, **사용자가 직접 켜야 해요.**
- 로그인·DB 쪽 통제는 로컬에서만 검증됐어요. 실제 Supabase 프로젝트에서는 아직 시험하지 않았어요.
