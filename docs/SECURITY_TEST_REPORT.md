# 보안 테스트 보고서

실행일: 2026-10-13. 모두 승인된 테스트 환경에서 했고, 운영 서비스와 운영 데이터에는 아무것도 보내지 않았어요.
- DB: 로컬 PostgreSQL 16.15, 매번 새로 만드는 테스트 DB
- 브라우저: 로컬 서버의 같은 앱 파일

## 환경과 명령
| 대상 | 환경 | 명령 |

**대역의 한계:** PostgREST(HTTP API, JWT 서명·만료 검사)와 GoTrue(로그인·MFA·세션)는 흉내 내지 않았어요. JWT의 내용(sub, role, aal)은 테스트가 직접 넣어요. 그래서 "토큰이 위조·만료됐을 때"는 이 시험 범위 밖이에요.

**1. 비로그인 사용자 (PASS, DB 계층)**
- 익명은 검증·미만료 가격 1건만 봐요. 검토 대기와 지난 이벤트는 안 보여요.
- 아래 15개 표는 읽기부터 권한 거부예요.
  - 감사 기록, 역할, 검토 기록, 수집 기록·정책, 신고
  - 이력 파티션 직접 읽기, 마이그레이션 기록
  - 사용자 표 7개
- 가격 추가·수정·삭제, `review_offer`, 신고, `delete_me` 모두 권한 거부예요.
- HTTP API 계층은 Supabase가 없어서 시험하지 않았어요.

**2. 다른 사용자의 데이터 (PASS)**
- 사용자 B에게 A의 데이터 7종이 0행이에요: 프로필, 기록, 장바구니, 항목, 패키지, 알림, 즐겨찾기.
- A의 id로 직접 걸러도 0행이에요.
- B가 시도해서 막힌 것
  - A 명의로 장바구니 만들기, A의 장바구니 이름 바꾸기·지우기
  - A의 장바구니에 항목 넣기, 자기 항목을 A의 장바구니로 옮기기
  - 자기 장바구니를 A에게 넘기기, A의 장바구니에 알림 걸기
  - A의 즐겨찾기 지우기, A의 프로필 고치기
- 시험 뒤 A의 데이터가 그대로인지 소유자 권한으로 다시 확인했어요.

**3. 가격 직접 변경 (PASS)**
- 로그인 사용자는 MFA까지 했어도 막혀요.
  - 가격 수정·삭제: 0행
  - 가격 추가·이력 쓰기: 거부
  - 검토 실행·검토 대기 보기: 거부
  - 처리 완료 상태로 신고 넣기: 열 권한 거부
- 시험 뒤 가격이 그대로였어요.

**4. 관리자 권한 얻기 (PASS)**
- 스스로 admin 부여, 역할 행 가로채기: 거부
- 일반 사용자는 역할 목록과 감사 기록을 0행으로 봐요.
- MFA 없이(aal1) 로그인한 관리자: 가격 수정 0행, 검토 거부
- MFA(aal2) 관리자: 수정 성공 → 감사 기록에 `10000 → 9000`과 관리자 id가 1건 남아요. 감사 기록 수정·삭제는 거부돼요.
- 검수자: 검토는 성공(기록 남음), 가격 직접 수정은 0행이에요.
- 수집 파이프라인(service_role) 변경은 `service_role`로 감사돼요.
- DB 소유자도 감사 기록을 고칠 수 없어요.
- 가격을 지워도 검토 기록은 남아요.

**5. 악성 입력 (PASS 7/7)**
- 넣은 곳
  - 가격 데이터의 상품명 4개(`<img onerror>`, `<script>`, `<svg onload>`, `<a href=javascript:>`)
  - 지점 이름, 원본 링크(`javascript:`), 지식 베이스 문장
  - 검색 주소
  - 공유 장바구니 링크: 악성 필드, `null` 항목, 수량 999, 깨진 base64, 3만 자, 깨진 `%`
- CSP 켬/끔 모두: 실행 0회, 대화상자 0, `javascript:` 링크 0개. 악성 문자열은 글자 그대로 보여요.
- 공유 링크를 저장하면 모르는 필드와 잘못된 항목은 버려지고, 수량은 20으로 잘려요.

**6. 대량 요청 (부분 PASS)**
- 사용자별 DB 한도는 작동해요: 신고 11번째 거절, 장바구니 31번째 거절, 128 KB 패키지 거절, 201자 기록 거절. 오류는 `quota exceeded`로만 나와요.
- **IP별 HTTP 요청 제한은 시험하지 않았어요.** 그런 기능이 아직 없어요(미해결).

**7. 만료된 세션 (미시험)**
- Supabase(PostgREST)가 JWT 만료를 검사하는데, 실제 프로젝트가 없어 시험할 수 없었어요. 로그인을 켤 때 아래 절차로 해야 해요.

**8. 브라우저 번들 (PASS)**
- `app/` 전체에 비밀 패턴이 0건이에요.
- `config.js` Supabase 키는 비어 있어요. 넣더라도 역할이 `anon`이 아니면 검사가 실패해요.
- service_role 문자열은 없어요.

**9. 공개 저장소 (부분 실패)**
- 현재 파일 92개는 0건이에요.
- **git 기록에서 예전 PIN이 발견돼요**(이전 커밋의 테스트 파일). PIN을 바꿔야 해결돼요.
- API 키·토큰·개인 키·JWT는 기록 전체에서 0건이에요.

**10. 백업 복구 (PASS)**
- 실제 데이터를 넣은 DB를 `pg_dump`(12 MB) → `pg_restore` 했어요.
- 아래가 모두 같았어요.
  - 표 7개 행 수(가격 62,417, 이력 62,417, 감사 76,678 등)
  - 전체 가격·이력 md5
  - 정책 85개, RLS 표 27개, 트리거 17개

**시나리오 7 절차 (로그인을 켤 때 dev 프로젝트에서)**
1. Supabase dev 프로젝트의 JWT 만료를 짧게(예: 60초) 정해요.
2. 로그인해서 access token을 받아요.
3. 61초 뒤 `GET /rest/v1/carts`에 그 토큰을 넣어요 → 401(JWT expired)이어야 해요.
4. 로그아웃(`signOut`) 뒤 refresh token으로 갱신을 시도해요 → 거절돼야 해요.

## 추가: 시술 지식 공개 규칙 (같은 날 추가, 시나리오 K)
- **K1:** 익명은 의료진 검수 완료(`published`) 항목만 읽고, 고칠 수 없어요.
- **K2:** 로그인 사용자는 의학 내용을 추가·수정·게시할 수 없어요.
- **K3:** 검수자는 초안을 볼 수 있어요.
- **K4:** 관리자도 검수자·검수일·출처 없이는 게시할 수 없고, 내용 수정은 감사 기록에 남아요.
- 공개 조건을 `true`로 약하게 바꾸면 `FAIL Ka`가 나서, 테스트가 실제로 잡아내는 걸 확인했어요.
