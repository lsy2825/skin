## 2. 설계 결정

**D1. 지금 스택을 유지하고 Next.js로 다시 만들지 않는다.**
요구사항이 "기존 스택 우선, 무분별한 재작성 금지, 낮은 인프라 비용"이에요. 정적 PWA + 주간 배치로 서버비 0원에 이미 가격 조회·비교·장바구니가 돌아가요.
서버가 꼭 필요한 기능(가격 알림 발송, 관리자 검증, 사용자별 저장)은 Supabase(무료 플랜)를 붙여 해결하고,
SEO 랜딩 페이지는 Python이 정적 HTML을 미리 만들어 같은 Pages에 올리는 방식으로 할 수 있어요.
재검토 시점: 관리자 화면·알림이 커져서 서버 렌더링이나 API가 꼭 필요해질 때.

**D2. 원본 → 정리 → 앱 데이터의 3단 분리, 원본 보존.**
`data2/raw`(원본, 매주 덮어씀)와 `data2/accepted`(검증 통과본), `data2/clean.csv`(정리본), `issues.csv`(정리 사유)를 따로 둬요.
정규화 전 값은 지우지 않아요. DB로 옮길 때는 같은 구조를 `offers`(현재) / `price_snapshots`(이력)로 나눠요(§4).

**D3. 같은 조건끼리만 비교한다.**
- 브랜드 간 비교는 수작업 규칙 36개(`xkeys.py`). 용량·샷·회차·원산지가 같은 1회 가격만 묶고, 테스트로 오매칭을 막아요.
- 그 밖은 **이름이 정확히 같은 옵션**(공백·단위 표기만 통일)을 3곳 이상이 팔 때만 자동 묶음(`groups.py`). 비슷하지만 다른 상품은 묶지 않아요.
- 단위당 가격(100샷당 등)은 참고로만 보여주고 기본 정렬에 쓰지 않아요(요구사항 3.2). 단위가 다르면 '조건 상이'로 빼요.

**D13. 시술 분류표로 모든 시술을 비교표에 넣는다 (2026-10-13 추가).**
- **배경:** 비교 탭이 수작업 키 36개만 보여줘서, 리쥬란도 힐러 2cc와 HB 플러스 1cc 두 가지만 비교할 수 있었어요.
- **구조:** `build2/taxonomy.py`가 가격 줄마다 아래를 정해요.
  - 제품군(family): 리쥬란, 사각턱 보톡스, 겨드랑이 제모 …
  - 세부 구분(tag): 국산/수입, 아이/바디, FX/FORMA, 힐러/HB …
  - 남은 단어
  - 용량, 회차
- **묶는 기준:** 이 다섯 가지가 모두 같고 3곳 이상이 팔 때만 하나의 비교 키(T…)로 묶어요.
- **같은 조건을 지키는 장치**
  - 사전에 없는 단어는 버리지 않고 남겨요. 이름에 다른 단어가 하나라도 있으면 따로 묶여요.
  - 단위를 모르는 숫자('4줄' 같은 것)도 남겨요. 그래서 수량이 다르면 절대 합쳐지지 않아요.
  - 키를 주지 않는 것: 묶음·패키지(제품군 둘 이상, '+', 패키지), 추가 옵션, 조건부 가격('300샷 이상 시'), 이용권·구독, 용량이 둘 이상인 이름, 국산과 수입이 함께 적힌 이름
- **수작업 키와의 관계:** 수작업 키는 그대로 우선이에요. 어떤 스펙의 줄 절반 이상이 이미 수작업 키에 맞으면 새 키를 만들지 않아요.
- **나누는 단위:** 보톡스·필러·제모는 부위별 제품군으로 나눠요(주름/스킨/사각턱 보톡스, 코/입술 필러, 겨드랑이 제모 …). 이름이 비슷해도 목적이 달라서, 한 목록에 섞으면 헷갈리기 때문이에요.
- **id:** 서명(signature)의 해시예요. 이름이 같으면 매주 같은 id라 장바구니·알림·즐겨찾기가 유지돼요. 이름이 바뀌면 새 키가 되고, 예전 키는 "가격 없음"으로 보여요.
- **사전에 없는 상품(2026-10-13 2차):** 제품군 사전에 없는 이름도 버리지 않아요.
  - 묶음·패키지(제품군 둘 이상, '+', '패키지', 괄호 안 ' + ')는 '패키지' 분류로, 이름 전체가 같은 것끼리 묶어요(예: '리쥬란 포함 패키지').
  - 단품은 이름 전체가 같은 것끼리 묶고, 이름을 제품군 이름으로 써요('기타' 등 해당 분류).
  - 제모는 옵션에 적힌 부위를 쓰고, 부위가 없으면 '부위 미표기 제모'로 둬요.
- **결과(2026-10-13 데이터):** 비교 키 36개 → 2,420개(수작업 36 + 분류표 2,384, 제품군 403개). 비교 키가 있는 가격 줄 6,768줄(11%) → 43,907줄(70.3%).
  - 나머지 13,043줄은 분류는 됐지만 같은 스펙을 파는 지점이 3곳 미만이라 비교 상대가 없어요.
  - 5,467줄은 일부러 빼요: 추가 옵션·구독권 5,025, 이용권·무제한 367, 조건부 가격 22, 이름 없음 53.
- **테스트:** `python build2/taxonomy.py`(39개, 워크플로에서 실행). 실제 데이터 점검 보고서는 `python build2/taxonomy.py --report` → `data2/variants_report.txt`.
- **기록:** 새 키의 주간 기록은 `data2/history/<date>.keys.json.gz`에 따로 압축해 둬요(주 126KB, 압축 안 하면 1.2MB).

**D14. 시술 설명은 가격과 분리된 지식 베이스에서 관리하고, 전문가 검수를 붙인다.**
- **위치:** `knowledge/treatments.json` 한 파일(항목 49개). 형식과 검수 방법은 `knowledge/README.md`.
- **항목 필드:** 쉬운 한 줄 설명, 일반적인 목적, 부위, 방식 차이, 브랜드·종류, 부작용, 주의사항, 근거 출처, 근거 메모, 검수 상태.
  - 공통 내용(예: 보톡스 공통 부작용)은 `base` 항목에서 물려받아요. 주름/사각턱/스킨/다한증 보톡스는 `base-toxin`을 물려받고 부위·목적만 달라요.
- **검수 상태:** draft(초안) / in_review / approved / needs_changes.
  - approved에는 검수자·검수일·출처가 꼭 있어야 하고, `build2/knowledge.py`가 배포 전에 막아요.
  - 지금은 49개 모두 draft예요. 앱은 모든 설명에 검수 상태와 "진단·효과 보장 아님, 의료진 상담" 문구를 붙여요.
  - 검수 의견은 앱의 "검수 의견 보내기"로 GitHub 이슈(템플릿 `knowledge-review`)를 열어요.
- **근거:** 공공기관·학회·리뷰 논문 13개 출처. 출처마다 확인일과 확인 방법(검색 요약으로 확인 등)을 적어요. 출처 없는 13개 항목은 '근거 자료 미정리'로 보여요.
- **원칙:** 효과를 약속하지 않고, 증상에 따라 시술을 권하지 않아요. 비교표("주요 종류 한눈에 비교")도 놓는 곳·목적만 나란히 보여줘요.
- **병원 설명:** 상품명 괄호 안 문구(3번 이상 나온 것)는 지식 베이스와 별도로 "병원 설명"이라고 밝혀서 보여줘요.
- **연결:** 항목은 제품군 이름(`families`)이나 분류표 기본 id(`fids`)로 비교 키와 연결돼요. 시술 사전·퀵뷰의 '가격 비교' 버튼은 그 제품군의 대표 키로 가요.

**D15. 최저가 표시 기준: '조건 없는 가격'만 대표가로 쓴다 (2026-10-13 추가).**
- **대표가(비교 화면 맨 위, 홈 카드):** 아래를 모두 만족하는 가격 중 가장 싼 것이에요.
  - 특가(체험가·한정가)가 아니에요.
  - 상품명에 조건 문구(첫 방문, 1인 1회, ○○원 이상 결제, 평일·시간, 단독 불가 등)가 없어요.
  - 종료일이 지나지 않았고, 급변 검토 대기도 아니에요.
  - 이번 주 수집에 성공한 지점이에요.
- **조건부 최저가:** 대표가보다 싼 조건부 가격은 "조건부 최저 ○○원"으로 따로, 조건 목록과 함께 보여줘요.
- **확인 필요 초저가:** 조건 문구가 없어도, 중간값의 30% 이하이면서 그 값을 1~2개 지점만 내는 가격은 대표가로 쓰지 않아요.
  - 같은 값을 내는 지점이 3곳 이상이면 체인의 보통 가격으로 봐요(예: 블리비 얼굴 점빼기 개당 100원, 조건 없는 가격 29곳).
  - 원본 대조에서 같은 이름·가격이 다시 확인되면(FOUND) 대표가로 쓸 수 있어요.
- **중간값:** 대표가와 같은 집합(조건 없는 가격, 지점마다 최저가 하나)으로 계산해요. 그래서 대표가가 중간값보다 비싸게 보이는 일이 없어요. '계산 기준' 버튼이 실제 지점 수와 계산식을 보여줘요.
- **원본 대조:** `scrape/verify_prices.py`가 초저가(중간값 30% 이하 또는 3,000원 미만)와 요청 예시 가격의 원본 페이지를 다시 읽어요.
  - 결과(FOUND / IN_BLOCK / NAME_ONLY / NOT_FOUND / FETCH_ERROR)는 이름·가격이 같은 줄에만 붙어요. 21일이 지나면 버려요.
  - FOUND = 상품명 뒤 160자 안, IN_BLOCK = 상품명이 든 가장 작은 블록(그 페이지의 다른 상품명은 없는 블록) 안. 페이지 글자는 요소 사이 공백을 남겨서 '49%' '990' '1,950'이 한 숫자로 붙지 않아요.
  - 결과는 가격 근거 시트의 '원본 대조' 줄에 보여요.
- **가격 이력과 정가 할인율은 따로:** 이력은 실제로 관측한 주간 스냅샷, 할인율은 병원이 적은 정가 기준이에요. 화면에서 다른 카드로 나누고 설명을 붙였어요.

**D16. 지도 위치의 정밀도를 밝힌다 (2026-10-13 추가).**
- 주소를 OpenStreetMap Nominatim으로 찾을 때 건물(도로명+번호) → 도로 → 구·동 순서로 시도해요(`scrape/branches.py`).
- 결과 단계는 `branches[9]`(0 건물 · 1 도로 · 2 구·동 · 3 없음)로 앱에 넘겨요. 2026-10-13 기준 건물 108곳, 도로 9곳, 구·동 1곳이에요.
- 도로·구 단계인 지점은 팝업에 "근사치예요, 주소를 확인하세요"라고 보여줘요.
- 좌표가 같은 지점(같은 건물 3곳, 도로 단계라 겹친 곳 2곳)은 확대하면 위아래로 나란히 놓아요. 그래서 하나씩 누를 수 있어요.
- 목록 → 지도 이동은 좌표가 아니라 지점 id로 팝업을 찾아요.

**D17. 보안은 구조의 일부로 둔다 (2026-10-13 추가).** 상세는 `docs/SECURITY_ARCHITECTURE.md`예요.
- 비밀번호 화면은 가림막일 뿐 접근 통제가 아니에요. 데이터와 저장소는 공개예요.
- DB 권한은 클라이언트가 아니라 DB 정책에서 판단해요(`supabase/DATABASE_ACCESS_POLICIES.sql`).
  - 스키마만 적용하면 잠긴 상태예요.
  - 관리자 쓰기는 역할 + MFA(aal2)가 있어야 해요.
  - 가격·역할 변경은 감사 기록에 남고, 그 기록은 추가만 가능해요.
- 브라우저: CSP(`script-src 'self'`), 수집 문자열은 글자로만 넣고, http(s) 링크만 만들어요.
- CI: 작업별 최소 권한, 외부 액션 SHA 고정, 배포 전 비밀 검사, DB 보안 시험 워크플로.

**D18. 피부 고민 찾기는 규칙 기반·검수 문장 전용으로 시작한다 (2026-10-13).** 상세: `docs/AI_CONCERN_DISCOVERY_SPEC.md`
- 생성형 AI를 쓰지 않아요. 분류는 낱말 사전으로 기기 안에서 하고, 의학 문장은 지식 파일에 미리 쓴 것만 보여줘요. 지어내는 의학 주장, 프롬프트 인젝션, 입력 유출을 구조로 막아요.
- 흐름: 위험 신호 → 고민 매핑 → 지식 항목 → 6단계 답변 → 사용자가 고른 시술 → 기존 가격 비교. 의학 정보와 가격 검색은 데이터가 섞이지 않아요.
- 검수 완료만 '검증된 내용'이에요. 초안 노출은 플래그로 정하고, DB는 published만 공개해요.
- 위험이 큰 기능(생성형 AI·광고·예약·공개 노출)은 법률 검토 전 플래그로 꺼 둬요(`docs/LEGAL_REVIEW_CHECKLIST.md`).

**D4. 데이터 무결성 우선.**
- 가격 그래프와 변동은 실제 주간 스냅샷만 써요. 빈 주를 채우지 않아요.
- 할인율은 병원이 직접 적은 정가가 있을 때만 보여요. 정가가 판매가보다 낮거나 10배를 넘으면 정가를 지워요.
- 가짜 데이터는 테스트에서만 써요. 앱 데이터에는 없어요.
- 새 수집 결과가 30% 넘게 줄거나 빌드가 실패하면 지난 자료로 배포해요.

**D5. 수집 정책.**
공개 페이지만 읽어요. 요청 간격은 0.7~1초, 동시 4개, 재시도 3회예요. 로그인·CAPTCHA·차단 우회는 하지 않아요.
robots.txt 확인은 Source Policy Registry(`scrape/sources.py` → `data2/sources.json`)가 수집 전에 해요(D8). 이용약관 검토일(`terms_reviewed`)은 사람이 채워야 해서 비어 있어요.

**D6. 지점은 독립 개체예요.** 같은 브랜드라도 지점마다 가격표를 따로 수집하고 비교해요(`branches` 배열과 지점별 URL).

**D8. 정확성 장치 (2026-10-13 추가).**
- 종료일이 지난 이벤트는 빌드 때 빼고(`issues.csv`), 앱도 오늘 날짜로 한 번 더 걸러요. 블리비처럼 금요일에 끝나는 이벤트 때문에 주말에 가격이 비지 않도록 종료 다음 날 아침 자동 재수집해요.
- 부가세는 행 이름의 표기 → 브랜드 기본값(`vat_policy.json`, 원문 인용·URL·확인일) 순서로 정하고, 근거가 없으면 '미확인'으로 둬요. 앱 기본 표시는 부가세 포함 예상가, 설정에서 병원 표시가로 전환.
- 지점마다 마지막 확인일과 상태(VERIFIED/STALE), 가격마다 출처 URL을 앱에 보여요.
- 지난주보다 90% 넘게 내리거나 10배 넘게 오른 가격은 사람이 승인할 때까지 비교에서 빼요(Human-in-the-loop, 파일 기반).
- robots.txt가 막으면 그 주 수집을 건너뛰고 지난 자료를 유지해요. crawl-delay를 요구하는 호스트는 주 1회 한 페이지만 읽어요.

**D9. 가격 계산은 `app/domain/pricing.js`.** 회차(첫 회만 특가), 패키지 묶음 수, 한 곳/여러 곳/최대 두 곳 최적화, 부가세, 종료일, 방문일 조건을 순수 함수로 두고 `tests/pricing.test.js`(node:test)로 검증해요. 화면 코드는 데이터를 모아 넘기고 결과를 그리기만 해요.

**D7. 법적으로 민감한 기능은 꺼 둔다.**
로그인과 회원정보는 `config.js`가 비면 꺼져요(feature flag). 예약·결제·광고·수수료 기능은 만들지 않아요.
시술 기록은 민감정보일 수 있어서, 켜기 전에 동의와 처리방침이 필요해요.

**D10. 편의 기능의 상태는 세 곳에만 둔다 (2026-10-13 추가).**
- **주소(URL):** 공유할 수 있는 상태. 화면, 검색어, 필터, 비교 시술(`#table?q=…&cat=…`, `#compare?k=X12`). 새로고침·뒤로 가기·링크 공유가 그대로 돼요.
- **기기 저장소(localStorage `pc:*`):** 사람마다 다른 상태. 장바구니, 즐겨찾기, 내 필터, 최근 검색, 정렬, 집·직장, 알림, 신고 기록. 로그인을 켜면 장바구니부터 서버와 병합해요(고유 id 사용).
- **메모리(`st`):** 그 화면에서만 쓰는 상태(펼침, 선택 탭).
- 화면은 이 상태로부터 매번 다시 그려요(`render`). 다시 그리는 중의 중첩 호출은 막아요.
- **누르는 동안엔 다시 그리지 않아요**(2026-10-14). 입력칸의 `change`/`focusout`이 같은 누름에서 화면을 갈면 손가락 밑 버튼이
  바뀌어 브라우저가 클릭을 보내지 않아요(예산·최소/최대 가격을 적고 칩을 누르면 무반응이던 원인). `render()`는 `pointerdown`·
  `mousedown`부터 그 클릭이 끝날 때까지(최대 1.5초) 미뤘다가 한 번 그려요. 폰은 포커스가 `pointerup` 뒤 합성 `mousedown`에서
  옮겨 가므로 둘 다 셉니다. 필터의 `go()`는 지금 주소에 덧붙여, 미뤄진 사이 누른 칩과 적은 값이 둘 다 남아요.
  검사: `tests/e2e/clickable.js`(가려진 컨트롤·입력 뒤 누름·반응 없는 요소·화면 오류, 회귀에 포함).

**D11. 확인 창 대신 되돌리기, 다시 그려도 포커스 유지.**
- 삭제·해지는 바로 실행하고, 6초 동안 "되돌리기"를 띄워요(`undoToast`).
- 이름 입력은 `prompt` 대신 시트(`nameSheet`)를 써서 칸 아래에서 검증해요.
- 시트(`sheet`)는 포커스를 안에 가두고, Esc로 닫고, 연 버튼으로 돌아가요.
- 같은 화면을 다시 그리면, 포커스가 있던 컨트롤을 이름표와 순서로 다시 찾아 포커스를 줘요(`focusMark`, `focusBack`).
- 터치 영역은 글자 크기를 키우지 않고 누르는 영역만 24×24px 이상으로 넓혀요(`.linkbtn::after`).

**D12. '인기'는 판매 지점 수예요.**
- 서버와 이용 통계를 두지 않기로 해서(D1, 개인정보 최소 수집), 인기 검색어는 파는 지점이 많은 시술로 정해요.
- 실제 검색량 순위는 서버 집계와 처리방침이 생긴 뒤에 할 수 있어요(`ADVANCED_UX_ROADMAP.md` P2).
