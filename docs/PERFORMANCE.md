## 해석

1. **이번에 실제로 좋아진 것은 R09 하나예요.** 느린 망에서 버전 확인이 막혀도 저장본 가격이 1.5초 안에 보여요(전: 31초). `fetchMeta`는 8초 뒤 포기하고 저장본을 계속 써요.
2. **첫 방문은 그대로예요(약 9초, 이 제한 조건에서).** 전송량 1.3MB 중 가격 데이터가 대부분이라, 이걸 줄이는 O2(홈 요약 분리)를 하지 않으면 바뀌지 않아요. 다음 단계 1순위예요.
3. **검색은 그대로예요.** 첫 검색 때 메인 스레드가 약 2초 막혀요(4배 느린 CPU 기준). O3(색인 사전 생성 또는 Worker)가 필요해요.
4. 재방문 중앙값이 91ms 늘었어요. 가장 느린 경우는 2.3초예요. 같은 조건으로 더 많이 반복해야 차이가 진짜인지 알 수 있어요. **개선이라고 주장하지 않아요.**

## O 항목별 상태

| ID | 조치 | 측정 근거 |
|---|---|---|
| O1 캐시 먼저 보여주기 + 메타 제한 시간 | 구현 | 메타 지연 재방문 31.5초 → 1.5초 |
| O2 홈 요약 데이터 분리 | 미구현 | 첫 방문 약 9초, 1.3MB가 그대로 |
| O3 검색 색인 / Worker | 미구현 | 첫 검색 2.3초, long task 약 2.1초 |
| O4 지도 지연 로딩 | 구현 | 전송량 −35KB. 지도 화면은 처음 열 때 Leaflet을 받음(로딩 표시) |
| O5 SW 캐시 정책 | 구현 | 설치 목록 축소, 자기 캐시만 정리. 실기기 업데이트 시험은 안 함 |
| O6 app.js 분리 | 일부 | 통계 함수 통합만. 측정 영향 없음 |
| O7 AI 기본 꺼짐·예산 예약 | 구현 | 성능 측정 대상 아님(DB 시험) |

## 브랜드 확대 뒤 (2026-10-14, 8개 체인·277곳·139,981행)

조건: `tests/perf/first_load.js`(gzip 서버, slow4g = 150ms·1.6Mbps·CPU 4배 느리게 / fast = 제한 없음), 3회. 전은 app.js 분리 직후 같은 도구 3회.

| 항목 (중앙값) | 전 (4개 체인·118곳) | 후 (8개 체인·277곳) |
|---|---|---|
| data.json gzip | 781KB | 1,879KB |
| slow4g 첫 방문 → 가격 표시 | 8,839ms | **16,160ms** |
| slow4g 전송량 | 1,312KB | 2,388KB |
| slow4g 재방문 → 가격 표시 | 2,140ms | 2,730ms |
| slow4g 누르기 반응 최대(INP 유사) | 256~272ms | 520~896ms |

**해석:** 데이터가 2.4배가 되면서 느린 망 첫 방문이 약 2배 느려지고, 휴대폰 CPU 조건에서 누르기 반응도 나빠졌어요(검색·필터가 더 많은 행을 훑음). 이 상태로 `main`에 합치면 비공개 베타 사용자가 체감할 정도라고 봐요(추측 — 실기기 측정 아님). 해결 1순위는 O2(홈 요약 데이터를 먼저 받고 전체는 뒤에서)이고, 다음은 O3(검색 색인 미리 만들기/Worker). 이번 작업에서는 데이터 반영까지만 했어요.
