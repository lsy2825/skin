# 피부 고민으로 찾기 — 기능 명세 (법률 검토용)

기준일: 2026-10-13. 대상은 윤실장의 '피부 고민으로 찾기'(`#concern`)예요. 위험 등급과 법률 질문은 `LEGAL_REVIEW_CHECKLIST.md`에 있어요.

## 1. 목적과 범위
**목적**
- 사용자가 자기 피부 고민과 관련된 **일반적인 시술 정보**를 이해하도록 돕는 거예요.
- 사용자가 **직접 고른** 시술의 가격을 객관적으로 비교하도록 돕는 거예요.
- 개인 맞춤 의료행위가 아니에요.

| 하는 것 | 하지 않는 것 |
|---|---|
| 자연어 고민을 분류해요(낱말 사전, 규칙 기반) | 개인 진단 |
| 시술 이름과 동의어로 연결해요 | 특정 시술이 그 사람에게 맞는지 판단 |
| 일반적인 시술 목적을 설명해요 | 주사 용량·횟수·개인 치료 계획 결정 |
| 시술 간 차이를 비교해요 | 효과 보장 |
| 근거의 종류와 한계를 안내해요 | 특정 병원의 결과가 낫다고 말하기 |
| 일반적인 부작용·주의사항을 설명해요 | 광고비에 따라 의료 정보 순서 바꾸기 |
| 시술 말고 할 수 있는 관리를 안내해요 | 예약·결제·환자 정보 전달 |

**지금 버전(MVP)의 위험을 낮춘 선택**
- **생성형 AI(LLM)를 쓰지 않아요.**
  - 분류는 낱말 사전(정규식)이고, 휴대폰 안에서만 돌아요.
  - 화면의 의학 문장은 모두 지식 파일에 미리 쓴 문장이에요. 실행 중에 문장을 만들지 않아요.
- 그래서 아래 위험이 생기지 않아요.
  - 모델이 의학 주장을 지어내는 것
  - 프롬프트 인젝션
  - 입력이 외부 서버로 나가는 것
  - API 키가 노출되는 것
- 생성형 AI 답변은 **만들지 않았고**, 플래그 `concernGenerativeAI: false`로 막혀 있어요(§8).

## 2. 처리 흐름 (지시서의 구조와 대응)
| 지시서 단계 | 윤실장 구현 | 파일 |
|---|---|---|
| User Concern | 자유 입력(최대 200자) 또는 고민 칩 선택 | `app/app.js` `views.concern` |
| Safety Classification | 위험 신호 규칙 3종(응급·자해·진료 권고)과 개인 판단 요청 감지 | `knowledge/concerns.json` `safety`, `app/domain/concern.js` |
| Concern Taxonomy Mapping | 고민 14종 × 동의어. 한 글자 낱말(점·털·땀)은 단어 단위로만 맞춰요 | 같음 |
| Reviewed Medical Knowledge Retrieval | 고민 → 시술 id → 지식 베이스 항목. 검수 상태별 노출은 플래그로 정해요 | `knowledge/treatments.json` → `data.json meta.kb` |
| Evidence-Based Educational Response | 6단계 고정 형식. 문장은 지식 파일 그대로 | `concernCard()` |
| User-Selected Treatment | 사용자가 '○○ 가격 →'를 직접 눌러요 | 같음 |
| Independent Price Comparison Engine | 기존 비교 화면. 같은 조건끼리 싼 순이고 기준을 공개해요. 고민 화면과 데이터가 섞이지 않아요 | `views.compare` |

**위험 신호 처리**
- **응급(빨강):** 숨쉬기·삼키기 어려움, 시야 이상, 얼굴 한쪽 마비, 필러·시술 후 피부색 변화·심한 통증 등이에요.
  - 진료·119 안내만 보여주고 **시술 정보는 보여주지 않아요.**
- **자해:** 자살예방상담전화 109와 정신건강위기상담 1577-0199를 안내해요.
  - 번호는 2026-10-13에 서울시 복지 누리집과 언론 보도로 확인했어요.
- **진료 권고(주황):** 고름·열, 점의 크기·모양·색 변화, 원인 모를 변화 등이에요.
  - 진료 안내를 먼저 보여주고, 일반 정보는 그 아래에 둬요.
- **개인 판단 요청:** "저한테 맞는", "몇 유닛", "무슨 병" 같은 표현이에요.
  - "어떤 시술이 맞는지, 용량은 진찰한 의료진만 정할 수 있어요"라고 먼저 밝혀요.
- 규칙은 `concerns.json`에 있어서 의료진이 직접 고칠 수 있어요.
- 한계: 낱말 규칙이라 표현이 다르면 놓칠 수 있어요(§10).

## 3. 시술 정보 형식 (Treatment Information Schema)
- 지식 파일의 필드를 지시서 필드명으로 바꾼 기록은 `python build2/knowledge.py --schema`와 DB 표 `treatment_knowledge`에 있어요.

| 지시서 필드 | 지식 파일(`treatments.json`) | 비고 |
|---|---|---|
| treatment_id | `id` | |
| treatment_name | `title` | |
| related_concerns | `concerns.json`의 `treatments`에서 거꾸로 만들어요 | 한 곳에서만 관리해요 |
| general_purpose | `purpose` | |
| mechanism_overview | `method` | |
| evidence_level | 출처 종류로 정해요: 공공기관·학회 → 리뷰 논문 → 의료기관 안내 → 없음 | **근거 문서의 종류**예요. 효과의 크기나 근거 등급(GRADE 등)이 아니에요 |
| limitations | `limitations` (+ 공통 항목에서 물려받음) | 2026-10-13 추가, 49개 모두 있음 |
| contraindication_information | `cautions` | 금기(절대 금기)와 주의사항을 아직 나누지 않았어요. 의료진 검수 때 나눠야 해요 |
| common_risks | `side_effects` | |
| source_references | `sources` (제목·기관·URL·확인일·확인 방법) | |
| medical_reviewer / reviewed_at | `review.reviewer` / `review.reviewed_at` | |
| publication_status | `review.status` (approved → published) | |

**검수된 정보만 '검증됨'으로 보여주는 규칙**
- **앱**
  - 검수 완료(approved)가 아닌 항목에는 항상 '초안 · 전문가 검수 전'이 붙어요.
  - `showDraftKnowledge: false`로 바꾸면 초안이 보이지 않아요. 시술 사전·퀵뷰·고민 화면 모두 해당하고, 테스트로 확인했어요.
  - 지금은 49개 항목과 고민 14개 모두 초안이라, 공개 출시 전에 검수하거나 끄는 게 필요해요.
- **DB**
  - `published`는 검수자·검수일·출처가 있어야만 저장돼요(CHECK).
  - 공개 API로는 `published`만 읽혀요(RLS).
  - 관리자도 검수 정보 없이는 게시할 수 없어요. 테스트 K1~K4로 확인했어요.

## 4. 답변 형식 (6단계, 고정)
1. **고민에 대한 일반적인 설명:** `concerns.json` `general`
2. **관련 시술과 시술 말고 할 수 있는 관리**
   - `non_procedural`을 먼저 보여주고, 그다음 관련 시술 이름을 보여줘요.
   - 순서는 분류표 순서이고, 화면에 "추천 순위나 효과 순위가 아니에요"라고 적어요.
3. **시술별 목적과 차이:** 표(시술 · 주로 받는 이유 · 방식과 차이)
4. **확인해야 할 위험과 한계**
   - 시술마다 주요 부작용, 한계, 주의를 보여줘요.
   - 근거 종류와 검수 상태 배지를 붙여요.
5. **관련 시술 자세히 보기:** 퀵뷰 시트. 부작용·주의 전체, 출처 링크, 검수 상태, 검수 의견 보내기가 있어요.
6. **직접 골라서 가격 비교하기**
   - 사용자가 누르면 비교 화면으로 가요.
   - 화면에 "같은 조건끼리 싼 순, 광고·협찬으로 순서가 바뀌지 않음, 특정 병원 추천 없음, 예약·결제·개인정보 전달 없음"을 적어요.

**금지 표현:** '가장 적합', 'AI 추천 1위', '맞춤 추천', '효과 보장' 같은 표현을 쓰지 않아요. 브라우저 테스트가 화면 전체에서 찾아내요.

## 5. 중립성
| 요구 | 구현 |
|---|---|
| 의학 정보와 병원 가격 검색을 따로 운영 | 고민 화면에는 병원 이름과 가격이 나오지 않아요(테스트로 확인). 가격은 사용자가 고른 뒤 비교 화면에서만 보여요 |
| 의학적 관련성을 광고비로 조정하지 않기 | 지식·고민 데이터와 DB 표에 광고·협찬 칸이 없어요. 고민 순서는 입력 낱말과 맞은 정도, 시술 순서는 분류표 순서예요 |
| 특정 병원을 기본 추천하지 않기 | 고민 화면에는 병원이 없어요. 비교 화면은 같은 조건 가격의 싼 순이에요 |
| 같은 조건의 검증된 가격만 비교 | 기존 비교 규칙(같은 비교 키, 대표가는 조건 없는 가격, 초저가 확인)이에요. `ARCHITECTURE.md` D3·D15 |
| 가격순 정렬 기준 공개 | 비교 화면의 '계산 기준' 시트 |
| 협찬과 일반 결과 구분 | 광고 기능이 없어요(`ads: false`). 만든다면 따로 표시해야 하고, 법률 검토 대상이에요 |
| 예약·결제·환자 정보 전달 없음 | 기능 자체가 없어요(`booking: false`) |

## 8. 생성형 AI를 붙인다면 (지금은 만들지 않음)
켜기 전에 모두 갖춰야 하는 조건이에요.
1. **서버 경유:** 키는 서버에만 두고(Supabase Edge Function 등), 로그인한 사용자만 쓰게 해요. 사용자별·IP별 요청 제한을 둬요.
2. **검색 결과만으로 답하기**
   - 같은 6단계 형식에 맞춰, 검수 완료(published) 항목의 문장을 인용·요약만 하게 해요.
   - 출처 id가 없는 문장은 화면에 내보내지 않아요(출력 검증).
3. **안전 분류는 모델보다 먼저:** 규칙 기반 위험 신호 분류를 지금처럼 앞에 두고, 응급이면 모델을 부르지 않아요.
4. **프롬프트 인젝션 대비**
   - 사용자 입력은 데이터 영역에만 넣어요.
   - 지시문과 검색 문서를 분리해요.
   - 출력에서 금지 표현과 개인 판단(용량·적합성)을 걸러요. 링크·HTML은 만들지 못하게 해요.
5. **저장 안 함 기본:** 입력과 출력을 기록하지 않아요. 품질 점검용으로 저장한다면 동의, 비식별화, 보관 기간, 민감정보 요건을 갖춰야 해요.
6. **표시:** '생성된 요약'임을 표시하고, 원문 지식 항목으로 가는 링크를 붙여요.

## 10. 한계 (모르는 것·안 된 것)
- **내용 검수:** 모든 문장이 의료진 검수 전 초안이에요. 고민 설명과 시술 말고 할 수 있는 관리는 제가 일반 정보로 썼어요. 출처가 없는 고민이 7개 있어요(여드름·흉터·홍조·건조·점·윤곽·문신).
- **놓칠 수 있는 표현:** 낱말 규칙이라 위험 신호도 표현이 다르면 놓칠 수 있어요(예: 사투리, 오타, 돌려 말하기). 반대로 과하게 걸릴 수도 있어요. 화면 위쪽에 진료 안내 문구를 함께 둬요.
- **금기와 주의:** 지금은 한 칸(`cautions`)에 같이 있어요.
- **근거 수준:** `evidence_level`은 문서 종류일 뿐, 근거 등급은 평가하지 않았어요.
- **법률 판단:** 이 문서와 체크리스트는 법률 판단이 아니에요. 면책 문구가 법적 준수를 뜻하지도 않아요.
